## 1. D-294：运行参数落库

### 1.1 修法

`ProviderClaimExtractor.extract()` 在 `build_request()` 之后、`provider.chat()` **之前**

### 1.2 三条设计约束（都写进代码注释了）

1. **旁路**：审计写失败**不阻断抽取**，但记 `AUDIT_WRITE_FAILED` 告警。
   理由：`append_audit` 抛异常或返回 `Err` 时，若静默吞掉，就变成
   "以为留痕了、其实没有"——比没有更糟。
2. **不改外发**：`detail` 只进 `audit_records`，**绝不进请求体**。
   `DeepSeekProvider._build_body()` 的"`metadata` 不发送"保持不变（那条注释是对的）。
3. **发送前写**：失败/异常的那次调用也要留下参数——"失败了"不等于"没发生"。

老 `usage_sink`（只有 `record_external_usage` / `has_external_usage` 两个方法）
**不因新增方法而失效**：用 `getattr(sink, "append_audit", None)` 探测，没有就跳过。

## 2. D-295：探针判定拆两行

### 2.1 旧判定的逻辑错误

```python
from_source = [e for e in evidence if e.get("source_id") == source_id]   # ← 先过滤
mentioning  = [e for e in from_source if about_name in e["claim"]]
```

`mentioning` 是从**已按探针源过滤**的列表里筛的，所以它的 `source_id` **必然正确**。
"`material_key` 对不对"这一项**结构上不可能被判错**——而 R4.7 恰恰错在这里
（探针句被归到百度宝玉页，`source_id` 不是探针源 ⇒ 从列表里消失 ⇒ 判"模型没选中"）。

### 2.2 新判定

1. 在**全部证据**里按字符 bigram Jaccard 定位探针句（阈值 0.5），**不按 `source_id` 过滤**；
2. 主体一行、`material_key` 一行，**分别判**；
3. 任一错 ⇒ `FAIL`；两行都对 ⇒ `OK`；全库找不到 ⇒ `WARN`。

输出形如：

```
探针材料：src_f13d8e…（属于「林黛玉」的检索结果）
该源已登记证据 4 条
定位到探针句（相似度 0.79）：贾宝玉自幼厌恶科举功名，把读书上进的人称作禄蠹，不肯走仕途经济之路。
[OK ] 主体：挂给了 贾宝玉（subject=['贾宝玉']）
[OK ] material_key：指向注入的那份材料（src_f13d8e…）
[OK ] 结论：…主体与归属都对
```

### 2.3 验证

**A. 用 R4.8 真实数据复算（零成本）**：

| 场景 | 结果 |
|---|---|
| 原样数据 | **OK**（相似度 0.79，主体 ✅、`material_key` ✅） |
| 把探针句 `source_id` 人为改成百度宝玉页（模拟 D-291 复发） | **FAIL**，且明确打出 `[OK] 主体 / [FAIL] material_key` + "D-291 的两段式核验失效" |

**B. 测试** `tests/test_p4_8_probe_judge.py` **11 项**，含用户点名用例
`test_wrong_material_key_fails_even_when_subject_is_right`（主体对、材料错 ⇒ FAIL）。

**C. 旧测试按新口径改写 5 处**（不是删）：

- 4 个用例的 `PROBE.text` 从占位符 `"探针"` 换成与证据同文的句子
  （定位改用文本相似度，占位符与任何 claim 相似度都是 0）；
- `test_evidence_from_other_sources_is_ignored` → 改名
  `test_evidence_from_another_source_fails_material_key`，断言由 `WARN` 改为 `FAIL`。
  **旧断言"忽略其他源"正是盲区本身**：过滤掉以后就再也发现不了"探针句被归到了别的材料"。

## 4. 产品化路线建议

### 4.1 现状盘点（已经有的，别重做）

| 能力 | 状态 |
|---|---|
| 五阶段业务链（研究→证据→人物→关系→对话） | ✅ `business run` |
| 装配层默认禁止真实外呼（`--allow-real`） | ✅ |
| 调用清单 `plan_calls`（花钱前看清单） | ✅ `business plan` |
| 逐笔账本 + 预算闸门 + 幂等 | ✅ |
| 任务六态 + 检查点续跑 | ✅ `task *` |
| 配置四级优先级 + 校验 | ✅ `config *` |
| 零第三方依赖 | ✅ 纯标准库 |

**缺的不是能力，是"普通人能用"。** 现在的入口是 `scripts/e2e_p4_8_real_search.py`，
那是实验脚本，不是产品。

### 4.2 三道坎（按优先级）

#### 坎一：质量稳定性（**最要命，先解决**）

R4.7 实测：材料逐字节相同、`temperature=0.7`，两轮证据只有 **4 条重合（Jaccard 8.0%）**。
这意味着**同一个输入跑两次，用户会得到两份不同的档案**——产品不能这样。

三个方案，建议 **C**：

| 方案 | 做法 | 代价 | 问题 |
|---|---|---|---|
| A 多次抽取取并集 | 跑 3 次，按 `(主体, tag)` 合并 | 模型成本 ×3（≈0.023 USD/次） | 证据更多但可能引入噪声 |
| B 低温 0.3 | 只改温度 | 零 | 仍未解决（0.3 也有采样），且牺牲覆盖 |
| **C 质量闸门 + 条件重跑** | 首次跑完检查 `traits` 条目数 / `REPEATED` 组数，**不达标才重跑一次并合并** | 平均 1.2~1.5×（≈0.011 USD/次） | 需要定义"达标线" |

**C 的达标线建议**（用已有数据定，不拍脑袋）：
- `REPEATED` 及以上组数 ≥ 1（R4.6 是 0，R4.7 是 1，R4.8 是 3）
- 或 `traits + habits + expression_style` 条目总数 ≥ 3
- 不达标 ⇒ 重跑一次，按 `(主体集合, tag)` 合并；**仍不达标就如实报"证据不足"**，
  不造假、不降门禁。

> 这条不解决，后面做多少 CLI 都是把不稳定包装得更好看。

#### 坎二：CLI 收口（产品门面）

现在的 `business run` 缺三个**用户一定会要**的开关：

1. **`--vocabulary`**：目前只能在 e2e 脚本里选 L1/L2。
   产品必须暴露（`--vocabulary l2-zh-classical`），否则中文古典角色拿不到
   `caustic` / `frail` / `rebellious` 这些标签。
2. **`--extract-temperature`**：默认 0.7，但要让人能调（调试/复现）。
3. **`--out`**：产物目录（现在只有 e2e 脚本有）。

再加两个**只读命令**（写档案之外，用户最常问的两件事）：

```
persona show  --project prj_x [--entity 林黛玉]      # 档案长什么样
persona evidence --project prj_x [--source src_xxx]  # 这条结论凭什么
```

以及一个导出：

```
persona export --project prj_x --format md|json --out ./out
```

**`persona export --format md`** 是产品化的关键一步：用户要的是"能贴进文档的东西"，
不是 SQLite 里的 JSON。建议输出结构：

```markdown
# 林黛玉

## 性格特征
- 有弱不禁风的一面（2 个来源：中青报、维基百科）

## 说话风格
- 言辞尖酸刻薄、喜欢怼人（1 个来源）
```

**每条都带来源数**——这是本项目的差异化：**不黑箱**。

#### 坎三：文档与分发

| 项 | 内容 | 优先级 |
|---|---|---|
| `README.md` | 5 分钟快速开始：装 → 配密钥 → 一条命令出档案 | P0 |
| `docs/QUICKSTART.md` | 三个完整示例（虚构角色 / 真人 / 自带材料） | P0 |
| `docs/FAQ.md` | 费用多少、为什么 traits 是 0、能不能离线、支持哪些模型 | P0 |
| `docs/VOCABULARY.md` | 怎么加自己的标签（L1/L2/L3 三层） | P1 |
| PyPI 发布 | 零依赖是卖点，`pip install generic-persona` | P1 |
| Docker 镜像 | 给不想装 Python 的人 | P2 |

**分发不建议一上来就 PyPI**：先让 3~5 个真实用户跑通（哪怕是从源码），
把"文档里没写但一定会踩的坑"收集完再发版。**发版容易，发一个让人装不上的版最难收场。**

### 4.3 建议的推进顺序

| 阶段 | 目标 | 验收标准 | 预估 |
|---|---|---|---|
| **P5.0** | 质量闸门（坎一方案 C） | 同一输入连跑 3 次，`traits` 条目数方差 ≤ 1；不达标重跑逻辑有测试 | 3~4 天 |
| **P5.1** | CLI 收口（三个开关 + `show`/`evidence`/`export md`） | 一条命令从零到 Markdown 档案；全程不需要看 e2e 脚本 | 4~5 天 |
| **P5.2** | 文档三件套 + 灰度 3~5 人 | 新人照着 README 能在 10 分钟内出第一份档案 | 3 天 |
| **P5.3** | PyPI + 发布流程 | `pip install` 后 `persona --version` 可用 | 2 天 |

**总计约 2~3 周。** 其中 P5.0 是**唯一有技术不确定性**的，其余都是工程量。

### 4.4 两条纪律（产品化阶段最容易破的）

1. **探针不进产品路径**。`--probe-*` 是验证工具，只在 e2e 脚本里；
   产品 CLI 不该出现，也不该把"探针注入过的材料"写进用户的库。
2. **"证据不足"必须如实说**。R4.6 的 `traits=0` 是正确行为（单源不得自证），
   产品不能为了"看起来有内容"把它填成 1 条。**空档案 + 明确原因** 好过 **1 条编出来的特征**。
