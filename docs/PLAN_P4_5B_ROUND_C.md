## 1. 结论摘要（先看这段）

C 轮不是一个实验，是**三个**，缺一个结论就不可信：

| 实验 | 形态 | 成本 | 回答什么问题 |
|---|---|---|---|
| **E1 阳性对照** | 离线，桩模型 + 三份真实材料 | 0 | **代码能不能**把"双人句"变成关系条目 |
| **E2 真实冒烟** | 1 次真实 POST | ≤0.0033 USD | **真实模型给不给**得出双人证据 |
| **E3 幂等重跑** | 同进程内重跑 | 0 | 重复运行会不会二次计费/二次写入 |

**核心设计判断**：E1 与 E2 是**正交**的。E1 失败 = 代码 bug；E1 通过而 E2 为空 =
证据不足。这是本文档对"如何区分链路通与证据不足"的正面回答（详见 §7）。

**第二个核心判断**：`traits` 在本轮**几乎必然为 0**，且这是**正确行为**，不是缺陷。
C 轮对 G6 的验收目标因此改成"每条证据都有 `stability_verdict`"（证明判定器
真的在真实链路被调用过），而不是"`traits` 非空"（详见 §8）。

**第三个核心判断**：C 轮验证的是**兜底路径**（未注入 `relationship_analyzer`）的
`shared_experiences` 产出。`perspectives` / `feeling_toward` 等条目属于 G-4 分析器
路径，真实链路当前**根本没装配分析器**，本轮不验证，也不该宣称验证过（详见 §10.3）。

## 3. "互动页"材料设计

### 3.1 定位

现有两份材料（`E2E_TEXT` / `E2E_TEXT_2`）**没有任何一句同时点名两人**——这是
上一轮已登记的硬事实。互动页是**第三个来源**（独立 URL、独立 `source_id`），
作用是提供可被抽成 `dimension=RELATION` 且主体覆盖两人的句子。

### 3.2 正文（5 句，每句 46–58 字，合计 **251** 字）

> 标题：`[合成样张·虚构] 雾港星灯会与灯塔值守旧例合记（非真实人物）`
> URL：`https://example.invalid/mist-harbor-lantern-night-joint-watch`

1. 据雾港志补记，星灯会与灯塔值守其实是一套旧例：每年灯会那一晚，阿雾与阿灯都要一同登上堤坝，从东头到西头逐盏核对灯位。
2. 核对灯位时两人话都不多，阿灯提灯照路，阿雾报出每一处风向与潮位，只在发现偏差时才会多说一句。
3. 老住户说，阿雾敲的铜钟就是灯会的开场信号，钟声三响之后阿灯才开始掌灯，这个配合已经沿用多年。
4. 有一年风暴夜里，阿灯独自护住整排灯架，阿雾在塔上整夜守着铜钟，直到风势减弱两人才在堤坝上碰面。
5. 灯会散场之后，阿灯会点亮最后一盏灯，再上塔把当夜的情形说给阿雾听，说完便各自回到自己的位置。

### 3.3 为什么这样写（每条都有对应理由）

| 设计 | 理由 |
|---|---|
| 每句都出现**两个人名** | 兜底路径要求 `subject_entity_ids` 覆盖 ≥2；只提一个人必然落进 `RELATION_EVIDENCE_SUBJECT_INSUFFICIENT` |
| 第 1 句是"共同例行" | 最容易被标成 `RELATION`（共同活动），且天然带两人 |
| 第 2 句写"互动方式"（话少、分工） | 覆盖"关系模式"，不是单纯共同出现（对应 RL 的"共现≠联盟"纪律） |
| 第 3 句复用已有事实（铜钟 / 掌灯） | 与另两份材料**不矛盾**，避免制造 `ConflictRecord` 噪声 |
| 第 4 句复用"风暴夜护灯架" | 让第 4 句成为第 2 份材料的**同一事件的另一视角**，测的是"跨材料一致"而不是重复登记 |
| 第 5 句写"散场后交接" | 提供非事件型互动（日常交接），提高 `RELATION` 而非 `EXPERIENCE` 的概率 |
| 句长 46–58 字、总字数 251（prose_chars 243） | 过正文门禁：`prose_chars ≥ 200`、`MIN_PROSE_LINE_CHARS = 40` |
| 无导航行、无列表、无标题行 | 导航行占比 `≤0.70`，实际为 0 |
| 全用合成名 | AC-16：源码与素材不得出现真实人物名 |

### 3.4 门禁自检（**已实测，不是估计**）

用产品门禁 `assess_content_quality(..., target_names=["阿雾","阿灯"])` 实跑这段正文：

```
status=VALID  reasons=[]  length=251  prose_chars=243
nav_line_ratio=0.0  anchor_link_ratio=0.0  longest_prose_run=243
page_type=GENERIC  target_mentioned=True
```

发送前仍须在运行里再断言一次（不能拿"设计时测过"当运行证据）：

- `quality_status == VALID`（三份全部）
- `prose_chars ≥ 200`、每行 ≥40 字
- `source_id` 已绑定且在本次 `source_ids` 内

> 若任一项不成立 → **不进第 7 步**，直接停止并报告。理由：材料被门禁拒收时，
> 真实模型仍会被调用（用更少的材料），这会产生"看起来跑通了"的假象。

### 3.5 进入材料流的接线方式（两个方案，需拍板 C-D1）

第三条查询从哪来？`plan_queries` 每目标产 1~2 条：基础词 +（**若有 `target.topic`**）话题词。

- **方案 1（推荐）**：给阿雾加 `topic`，得到第三条查询 `阿雾 <topic>`，
  桩按**精确查询文本**返回互动页。
  3 查询 / 3 抓取 / 每查询 1 条结果 → **完全确定性**，不依赖排序。
- **方案 2**：让阿雾那条查询返回 2 条结果，互动页是第 2 条。
  需要 `max_results_per_query=2`，且要看 `filter_and_rank` 的确定性排序是否会把它挤出
  `max_extracts`。**多一处依赖，少一分可信**。

推荐方案 1，研究上限改为 `max_queries=3, max_results_per_query=1, max_extracts=3`。

## 5. 三个实验的执行顺序

```
E0  --dry --path=orchestrator --names 阿雾,阿灯        （0 成本，材料 3 份、五阶段全 EXECUTED）
  ↓   断言：材料 3 / 全 VALID / 目标 2 / 桩模型 0 次真实调用
E1  离线阳性对照（桩模型返回双主体 RELATION）           （0 成本）
  ↓   断言：shared_experiences ≥1 且关系档案 status = OK
  ↓   若 E1 红 → 停止，这是代码 bug，不是证据问题
E2  真实冒烟（1 次 POST，不重试）                      （≤0.0033 USD）
  ↓   记录：request_id / token / 费用 / accepted / rejected / pending
  ↓   四层计数 → 判定矩阵 → 归因
E3  幂等重跑（同进程）                                 （0 成本）
  ↓   断言：真实调用数不变、命中 DUPLICATE_SKIPPED 或 BUDGET_EXCEEDED
E4  独立复算 + 报告
```

**为什么 E1 必须在 E2 之前**：E1 若在 E2 之后跑，一旦 E2 为空，你会先花钱再证明
"代码没问题"——而"代码没问题"这个前提本来可以免费拿到。

## 6. 预算

### 6.1 预留与实际

| 项 | 值 |
|---|---|
| 预留（发送前冻结） | 3000 in × 0.3/1M + 2000 out × 1.2/1M = **0.0033 USD** |
| 实际预估 | in ≈1200–1700、out ≈900–1300 → **0.0015–0.0020 USD** |
| 硬上限 | **0.25 USD**（`PERSONA_MODEL_MAX_COST` / `_PER_TASK`） |
| 调用上限 | **1 次**（`PERSONA_MODEL_MAX_CALLS=1`），失败不重试（`max_retries=0`） |
| 上轮实测参照 | in 859 / out 849 → 0.0012765 USD（本例材料多 2 份，输入会上升） |

### 6.2 成本增量来源

多出的两份材料（互动页 251 字 + 阿灯页 249 字）增加输入约 350–550 token
（上轮实测：1 份 254 字材料 → in 859）；
产出候选从 6 条增到约 10–14 条，输出约 +150–350 token
→ 增量上限约 **+0.0006 USD**，不改变 0.0033 这个预留数量级（仍在 0.0020 以内）。

### 6.3 一个必须说清的账本事实

`ExternalUsageLedger` 是**纯内存**实例（`usage_ledger.py:292`，无任何落盘）。
所以"检查历史支出、预留不重置账本"在当前实现下**在进程层面是不成立的**——
每次 `--run` 都是全新账本，"累计"没有任何载体。

本轮的实际做法（诚实版）：

- 额度按**单次运行**生效：`max_cost=0.25` 是本次运行的上限；
- 跨运行累计**只能人工记账**：上轮 0.0012765 USD + 本轮预估 ≤0.0033 → **累计 ≤0.0046 USD**；
- 报告里必须写出这两个数字，并注明"非系统自动累计"；
- 若你要的是系统级累计闸门，那是一个**新缺口**（建议登记 G11），不在 C 轮修。

## 7. 关系条目产出路径如何被验证（本轮最核心的部分）

### 7.1 四层探针

关系条目从"材料里的一句话"到"档案里的一条"要过四道：

| 层 | 观测量 | 取数位置 | 为空意味着 |
|---|---|---|---|
| **L1 材料** | 进入材料流份数 / 带门禁结论份数 | `[4]` 段 `进入材料流 N 份（其中带门禁结论 N 份）` | 研究/门禁问题（与模型无关） |
| **L2 抽取** | accepted 中 `dimension=RELATION` 的候选条数 | `run` 产物 `extraction.claims` | 模型没读出来（证据不足） |
| **L3 主体** | 上述候选中 `subject_entity_ids` 覆盖两人的条数 | 同上 | 模型读出的是单人视角（证据不足） |
| **L4 写入** | `shared_experiences` 条数 + 档案 `status` | `run.relationship_profile_ids` → 回读档案 | **L2/L3 都有而 L4 空 = 链路故障** |

### 7.2 判定矩阵（把"空"归因到唯一原因）

| L1 材料 | L2 RELATION | L3 覆盖 2 人 | L4 条目 | 结论 | 对应告警码 |
|---|---|---|---|---|---|
| 3 份 VALID | ≥1 | ≥1 | ≥1，`status=OK` | **链路通** ✅ | — |
| 3 份 VALID | 0 | — | 0 | **证据不足（模型未产出双人维度）** | `NO_RELATION_EVIDENCE` |
| 3 份 VALID | ≥1 | 0 | 0 | **证据不足（单人视角描述）** | `RELATION_EVIDENCE_SUBJECT_INSUFFICIENT` |
| 3 份 VALID | ≥1 | ≥1 | 0 | **链路故障** ❌ 必须当 BUG 处理 | 无专项码（漏报）或 `RELATION_EVIDENCE_UNUSED_OTHER` |
| <3 份 | — | — | — | **未通过前置**，不进入归因 | `MATERIAL_GATE_REJECTED` / `MATERIAL_SOURCE_UNBOUND` |

> 第 4 行是本轮唯一需要"修代码"的分支，而且它是**可判定的**——这正是 E1 存在的意义：
> E1 若绿，第 4 行在真实运行里出现就一定是别的东西（例如被 G7 降级拦下），
> 而 G7 会留下 `RELATIONSHIP_DEGRADED_SKIPPED`。

### 7.3 E1 阳性对照的具体设计

- 输入：**同一份**三材料（走同一个 `Stack`、同一条 `BusinessOrchestrator.run`）
- 模型：桩 `StubChatProvider`，返回 8 条候选，其中
  - 2 条 `RELATION` + `VERBATIM` + 逐字引用互动页第 1、4 句 + `subject_entity_ids=[阿雾, 阿灯]`
  - 其余 6 条为单人 `BACKGROUND/HABIT/TRAIT`
- 断言：
  1. `len(relationship.shared_experiences) == 2`
  2. 档案 `status == OK`
  3. 每条 `shared_experiences[i].evidence_refs` ⊆ 本次 `evidence_ids`
  4. `real_chat_calls == 0`（桩，零成本）

**E1 绿 ⇒ "代码能把双人证据变成条目"这件事已被证明**，与真实模型无关。
这就是"链路通"的可证伪定义。

## 8. `traits` 是否可能仍为 0？

**会，而且几乎必然为 0。这是设计使然，不是缺陷。**

推理链（每一环都有代码依据）：

1. 判定键 = `(归一化 claim, 主体集合)`，组内**按 `source_id` 去重**（G6-D2）；
2. `judge_stability` 的语义：`occurrences=1 → SINGLE`、`≥2 → REPEATED`、`≥3 个不同来源 → PATTERN`；
3. 去重后 `occurrences` **恒等于**来源数 ⇒ 要 `REPEATED`，同一句（归一化后完全相同）
   必须来自 **≥2 个不同来源**；
4. 三份材料的正文互不重复（互动页是"合记"，措辞与另两份不同）；
5. 归一化只折空白，**不做语义聚类** ⇒ 措辞不同即不同组；
6. ⇒ 每条 TRAIT 证据都 `SINGLE` ⇒ 按 AC-7 **绝不进 `traits`** ⇒ `traits = 0`。

**即使**把同一句原话抄进两份材料，模型输出的 `claim` 是它自己的概括，也**不保证**
两处措辞完全一致——所以这条路不可靠，不该写进验收。

### 8.1 C 轮对 G6 的验收目标（可达成且有意义）

| 不验 | 改验 |
|---|---|
| `traits` 非空（不可控） | **每条证据都有 `stability_verdict`**，且 `occurrences==1`、`distinct_sources==1`、`stability==SINGLE` |
| — | `stability` 列**仍为** `UNKNOWN`（原值未被覆盖，可追溯性成立） |
| — | 无 `STABILITY_UNASSESSED` 告警（证明判定全部成功，没有静默退回） |

这三条**恰好**是 G6-D1 那个决策（另开字段、不改原列）的运行时证据。

### 8.2 要验证 `traits` 路径怎么办

那是另一个实验，需要"同一事实在 ≥2 个独立来源出现"。三条可行路径，**均不在 C 轮**：

- **C+**：专门设计"同句多源"材料（两份来源含**逐字相同**的句子，且引导模型用同一措辞）；
- **种子路径**：`evidence_seeds` 显式声明 `REPEATED`（可验路径，但绕过了抽取）；
- **语义聚类**：需要模型做 claim 归一（新能力，新轮次）。

| # | 条件 | 处理 |
|---|---|---|
| R1 | `accepted == 0` | 停止。抽取整体失败，不允许推断关系链路 |
| R2 | 费用 `cost_confirmed` 为空或 `> 0.25` | 停止，人工对账 |
| R3 | 任一阶段非 `EXECUTED`（双人物下应为 5/5） | 停止，按阶段定位 |
| R4 | 判定矩阵落到"链路故障"行 | 停止，当 BUG 登记，不通过"再跑一次"掩盖 |
| R5 | 摘录核验失败（`rejected` 里出现 `VERBATIM_QUOTE_NOT_FOUND` 类） | 记录并继续，但必须在报告里逐条列出 |

**E3 幂等重跑的唯一例外**：它本身就是为了"被拦住"而设计的，被拦下是**通过**。

## 10. 验收标准（分三级，避免"全是必须"导致误判）

### 10.1 甲级：必须满足，任一不过即验收失败

1. 恰好 **1 次**真实 POST；`request_id` 已记录
2. `cost_status=CONFIRMED`、`cost_source=OFFICIAL_RATE`、费用 ≤ **0.25 USD**
3. 五阶段全 `EXECUTED`，整体 `SUCCEEDED`
4. 材料 **3 份**，全部 `VALID` 且已绑定来源
5. `accepted ≥ 1`；`rejected` / `pending` 逐条列出原因
6. 人物档案 **2 份**；每条证据都有 `stability_verdict`，`stability` 列未被改写
7. 关系档案 **1 份**：`cardinality=PAIR`、参与者 = 2、`status ∈ {OK, INSUFFICIENT_EVIDENCE}`
8. 关系档案为空时，**必须**命中 §7.2 的"证据不足"分支，并带对应告警码
9. E3：真实调用数不变（`DUPLICATE_SKIPPED` 或 `BUDGET_EXCEEDED`）
10. 原始响应落盘（`<dump>.raw.json`，请求头只记名不记值）
11. 独立复算器全绿（含新增的关系与稳定性检查）

### 10.2 乙级：期望满足，不满足不判失败但必须解释

12. `shared_experiences ≥ 1` 且关系档案 `status = OK`（即"真实模型确实抽出了双人句"）

### 10.3 丙级：允许为空，但必须在报告里写明原因

13. `traits = 0` —— 预期结果，理由见 §8；**不得**因此判为失败
14. `perspectives` / `feeling_toward` 全空 —— 兜底路径**从不**产出这些字段
    （`_relationship_draft_fallback` 只填 `shared_experiences`）。
    它们属于 G-4 分析器路径，真实链路未装配分析器，**本轮不验证也不宣称验证**

## 11. 隔离与回滚

| 项 | 做法 |
|---|---|
| 数据库 | `Stack` 用 `tempfile.mkdtemp("gps-p45a-")`，`teardown()` 里 `rmtree`；进程异常退出也不污染仓库 |
| 产物 | `--dump` 默认落 `%TEMP%`（G10 已修）；本轮建议显式 `%TEMP%/p45b_pair_run.json` |
| 原始响应 | 同目录 `p45b_pair_run.raw.json` |
| 仓库 | 不写 `var/`、不写 `.log`、不写 `.db`；回归日志写 `%TEMP%` |
| 账本 | 纯内存，进程结束即消失；无残留额度、无脏预留 |
| 失败回滚 | 无需回滚（临时库随进程消失）；若中途 Ctrl-C，临时目录由系统清理 |
| 禁止动作 | 不 `rm -rf`、不清空任何既有库、不覆盖 `.env`、不改 `.gitignore` |

**风险点**：`%TEMP%/p45a_evidence/` 里还留着 P4.5-A 的两份验收证据（10082 B / 4560 B）。
本轮产物用**不同文件名**（`p45b_pair_run*`），不复用、不覆盖。

## 13. 需要拍板的决策点

| # | 决策 | 我的建议 | 理由 |
|---|---|---|---|
| **C-D1** | 互动页作为**第三条查询**（给阿雾挂 `topic`）还是**第二条结果** | **第三条查询** | 完全确定性，不依赖 `filter_and_rank` 的排序；多一条桩查询零成本 |
| **C-D2** | 是否允许改动抽取提示词，补一句"涉及多人互动的标 RELATION" | **不改** | 改了就不是"测量真实行为"，而是"引导模型给出想要的答案"；若 R1 发生，把它当**测量结果**记录 |
| **C-D3** | 关系条目是否列为**甲级**验收 | **列乙级（期望）** | 模型行为不可控；把它列甲级会逼着后续去"调材料直到成功"，那是拟合 |
| **C-D4** | C 轮是否顺带注入 `RuleRelationshipAnalyzer` | **不注入** | 那是产品装配改动（新接线），应另立 C+ 轮单独验收；本轮保持"兜底路径"单一变量 |
| **C-D5** | `traits=0` 是否在验收记录里写成"预期" | **是，明确写** | 否则未来每次冒烟都会被误读成回归 |
| **C-D6** | 复算器扩展范围 | 多目标 + `REL.*`（3 项）+ `STAB.*`（2 项） | 关系结论与稳定性结论都必须可独立复算，否则又是"自证" |
| **C-D7** | 费用累计是否登记 G11 | **登记，不修** | 修累计闸门涉及账本持久化，是设计变更，不该混在冒烟轮 |

## 15. 一句话总结

C 轮的价值不在于"跑出关系条目"，而在于**让"跑不出来"这件事变得可解释**：
E1 证明代码能，E2 测量模型给不给，判定矩阵把空归因到唯一原因，
`traits=0` 被写成预期而不是缺陷。**任何一条不满足，报告里都必须写出是哪一层断的。**
