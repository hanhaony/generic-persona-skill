## 1. 实际调用 vs 清单

| 项目 | 清单 | 实际 | 判定 |
|---|---|---|---|
| 检索 `/search` | 2 | **2** | ✅ |
| 抓取 `/extract` | ≤ 1 | **2** | ❌ **超清单** |
| 模型 `chat/completions` | ≤ 2 | **2** | ✅ |
| 合计往返 | — | 6 | — |

**抓取为什么是 2 次（这是清单口径问题，不是产品失控）**

两次抓的是**同一个 URL**（`http://www.purepen.com/hlm`）：

1. **初始抓取 1 次**（`max_extracts=1`），返回正文过短，被门禁判 `TOO_SHORT`
2. **补救抓取 1 次**（`max_remediations=1`），仍不过门禁（`TARGET_NOT_MENTIONED`），官方计费 0

产品的两条额度是**独立**的：

```python
# persona/config/spec.py:192
max_remediations: int = 1   # 每个 URL 最多补救几次

# persona/modules/research.py:1577（_remediate_low_quality 文档）
# 2. **次数**：每 URL 最多 `max_remediations` 次；本轮补救发送总量
#    ≤ `max_extracts`（D2：补救是同一篇的第二次抓取，不占初始名额，
#    但也不能无限膨胀）。
```

所以"抓取总量"= `max_extracts` + 补救 ≤ 2。**授权清单写"≤1 次抓取"漏算了补救额度**，
脚本自检按字面判 `2 > 1` 为清单外调用——判定本身没错，错在清单口径。
本轮补救没多花钱（第二次 0 credit），但**下次写清单必须写"≤1 初始 + ≤1 补救"**。

> 这不是"清单外调用即缺陷"所指的产品越界：没有任何一次请求超出 `research.*` 配置，
> 也没有任何域外 URL。是清单的计数口径与产品口径不一致。

## 2. P0 缺陷：主体归属 100% 错绑

### 2.1 现象

`pe_cb22…` = 林黛玉、`pe_b815…` = 贾宝玉（数据库 `PersonEntity` 确认）。
落库证据却是：

| 内容讲的是谁 | 条数 | 被标成谁 |
|---|---|---|
| 贾宝玉 | 15 | **全部标成林黛玉** |
| 林黛玉 | 5 | **全部标成贾宝玉** |
| 双主体（"宝玉与黛玉青梅竹马"） | 1（#4） | 正确（两个 ID 都挂）✅ |
| 双主体但只挂一个（#7 / #22） | 2 | 错 |
| 无人物（网页/回目描述，#17/#24/#25） | 3 | 被硬挂人物 ID（次要问题） |

**26 条里只有 #4 一条主体正确。**

### 2.2 后果：两个 traits 条目互相张冠李戴

落库档案（`PersonaProfile`）：

| 实体 | traits | 内容实际是谁的 |
|---|---|---|
| `pe_cb22…`（黛玉） | 1 条："贾宝玉厌恶四书和八股文…称作禄蠹" | **贾宝玉的** ❌ |
| `pe_b815…`（宝玉） | 1 条："林黛玉被描述为富有诗意美和理想的悲剧形象" | **林黛玉的** ❌ |

**最危险的地方：条目数完全对得上**（黛玉 1 traits + 1 single_event = 2；宝玉 1 + 5 = 6），
组数也对得上。如果只对"数量"验收，这轮会被判通过。

### 2.3 根因（不是模型乱猜，是提示词没给信息）

发给模型的 system message（`raw_responses.jsonl` 第 5 条）里，主体段原文只有两行：

```
本次允许使用的主体 ID：['pe_cb2223c7d04641a3a1916ebf2eee2e03', 'pe_b815ddcb6621479bb1b9dc5f93386296']
subject_entity_ids 只能从上面这个列表里选，不得自造 ID。
```

**没有任何"ID ↔ 显示名"的对应关系。**模型从材料里读到"贾宝玉…"，要在两个裸 ID 里选一个——
它没有任何依据，只能按列表顺序猜。本轮它把"贾宝玉"猜成了列表第一个（黛玉），
于是所有宝玉说法进了黛玉档案；反过来黛玉说法全进了宝玉档案。

代码位置（`persona/modules/extraction.py:1233-1236`）：

```python
allowed = target_ids_of(targets)
if allowed:
    lines.append(f"本次允许使用的主体 ID：{allowed}")
    lines.append("subject_entity_ids 只能从上面这个列表里选，不得自造 ID。")
```

`targets` 里本来就带显示名（`pe_cb22…` 对应"林黛玉"），只是没写进提示词。

### 2.4 为什么 R4.4 没暴露（这点很重要）

R4.4 的 system message **是同一段代码产出的，同样只有 ID 列表**（已核对 r44 原始响应）：

```
本次允许使用的主体 ID：['pe_982dde36…', 'pe_74b440ae…']
```

但 R4.4 的 22 条单主体证据**全部正确**。原因是上一轮的检索结果里，
"林黛玉 红楼梦"返回了黛玉的人物专页，材料内容与材料目标一致，
模型按"材料顺序 ↔ 目标顺序"的隐含对应就能蒙对。

本轮"林黛玉 红楼梦"的 5 份结果里，**只有 1 份与黛玉直接相关**（CCTV 剧集页），
另外 4 份是《红楼梦》总页 / 维基文库回目——内容大量在讲贾宝玉。
材料目标与材料内容一旦错位，"按顺序蒙"立刻失效。

**结论：R4.4 的主体正确是无保证的正确。这是结构性缺陷，不是本轮回归。**

### 2.5 修复方案

1. **P0（零成本，必做）**：system prompt 注入映射，形如
   `本次允许使用的主体：林黛玉 = pe_cb22…、贾宝玉 = pe_b815…`，
   并保留"只能从列表选"的约束。
2. **P1（可选，成本高）**：抽取后加主体一致性门禁——claim 文本里明确出现另一个目标的名字、
   却没有把它列为 subject 时告警（`SUBJECT_CONTENT_MISMATCH`）。
   这条能兜住"提示词没修好"或"模型不听话"的情况，但要防误伤（双主体说法）。
3. **P2**：无人物 claim（网页/回目描述）不该硬挂人物 ID，可要求 `subject_entity_ids` 允许为空。

### ① "尖酸刻薄"是否贴成 `caustic` 而不是 `witty` —— **无法验证：本轮材料里根本没抽出这条**

26 条证据里没有任何一条讲黛玉的言辞方式。逐条看黛玉（内容口径）的 5 条：

| # | 维度 | 标签 | 内容 |
|---|---|---|---|
| 18 | CANON_FACT | — | 央视版第 1 集名为"林黛玉别父进京都"，黛玉由陈晓旭饰演 |
| 19 | EXPERIENCE | — | 林如海之妻去世后，黛玉由贾雨村护送至京都荣国府 |
| 20 | TRAIT | `knowledgeable` | 博览群书、学识渊博，有多种才能 |
| 21 | TRAIT | `melancholy` | 被描述为富有诗意美和理想色彩的悲剧形象 |
| 23 | TRAIT | `melancholy` | 禀赋多愁，才藻绝伦 |

**没有"言辞尖酸"这类说法。**原因是检索侧：黛玉的 5 份材料里 4 份是《红楼梦》总页/回文，
没有人物专页，而"尖酸刻薄"这类评价只出现在人物专页的性格段。

所以这条**既不能算贴对、也不能算贴错**——它是"素材没给到"。
要验证 `caustic` 是否会被正确选用，得让检索先拿到黛玉的人物专页（见 §5 建议）。

### ② 黛玉 `expression_style` 是否非空 —— **❌ 仍为空（0 条）**

落库黛玉档案 `expression_style: 0`。纠正主体后也还是 0：全轮唯一的 SPEECH_STYLE
证据是 #13"编新不如述旧，刻古终胜雕今"（宝玉的文学主张），黛玉侧没有言辞类证据。

对照 R4.4 回放变体 B 的预期（重贴后黛玉 `expression_style` 首次非空）——
**回放的前提是"材料里有黛玉的言辞说法"，本轮材料没有**，所以这个预期无法在本轮兑现。
这不是 L2 的问题，是检索供给的问题。

### ③ 黛玉 traits 是 1 还是 2 —— **数字是 1，与回放变体 B 预期一致；但落库那条内容是宝玉的**
