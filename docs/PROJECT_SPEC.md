## 1. 背景与目标

### 1.1 要解决的问题

要让「多个真实人物」在一场模拟对话里说话，难的不是生成文本，而是：

1. 这些人的性格、说话风格、共同经历从哪来？
2. 怎么保证不是凭空编的？
3. 两个人之间的关系怎么表达？同一件事双方视角不同怎么办？
4. 对话产生的"新事件"能不能当成真事？
5. 聊了很多轮之后，怎么记住之前的事？

### 1.2 产品目标

| 编号 | 目标 | 可验证方式 |
| --- | --- | --- |
| G-1 | 用户只输入 2 个或更多人名，系统自主完成资料搜集与档案构建 | CLI 单条命令可跑通全流程 |
| G-2 | 普通用户零审核负担 | 全流程中，用户不需要回答任何"请确认这条证据"的问题 |
| G-3 | 内部可追溯 | 任一档案条目可反查到来源；任一来源可反查到它支撑了哪些条目 |
| G-4 | 冲突可见但不可怕 | 冲突被记录，流程不中断，不需要裁决 |
| G-5 | 模拟与真实严格分离 | 存在自动化断言，证明模拟内容无法写入真实证据库 |
| G-6 | 长期可运行 | 支持记忆、预算、断点续跑、自动化测试 |
| G-7 | 通用化 | 代码与配置中不含任何特定人物的硬编码内容 |

## 3. 用户流程（User Flow）

### 3.1 主流程

```
Step 1  建任务
   $ persona new --names "人物A, 人物B[, 人物C...]" [--topic "可选话题"]
   系统返回：run_id、任务计划（将执行哪些阶段）、预算预估

Step 2  自动研究（用户只需等待进度条）
   输出：  [2/6 研究]  已登记 23 个来源，去重后 17 个
           [3/6 证据]  提取 84 条证据，其中 5 组冲突已记录

Step 3  档案构建（用户无感知，只显示完成状态）
   输出：  [4/6 人物档案]  2 个人物档案已生成
           [5/6 关系档案]  1 组关系档案已生成（含 2 个视角）

Step 4  进入对话
   $ persona chat <run_id>
   系统自动决定发言者与内容，逐轮输出；用户可随时插入一句话

Step 5  收尾
   $ persona status <run_id>      查看任务状态与预算消耗
   $ persona sources <run_id>     按需查看来源清单（可选，不强制）
   $ persona forget <memory_id>   删除某条记忆
```

### 3.2 异常流程

| 情况 | 系统行为 |
| --- | --- |
| 名字有歧义（重名） | 记录候选与不确定性；**待定 Q-01**：是否中断询问用户 |
| 找不到足够资料 | 标记该人物 `INSUFFICIENT_EVIDENCE`，档案标注"资料不足"，**流程继续**，不报错退出 |
| 来源互相矛盾 | 全部保留，生成冲突记录，标记 `uncertainty`，**不阻断** |
| 预算耗尽 | 暂停任务，保存检查点，提示用户；**待定 Q-07**：是否自动降级 |
| 中途崩溃 / Ctrl+C | 已完成的阶段结果落盘，可用 `persona resume <run_id>` 续跑 |

## 4. 功能范围

### 4.1 人物档案（Persona）必须覆盖

| 维度 | 说明 |
| --- | --- |
| 背景 | 身份、职业、所处环境、时代背景等 |
| 性格 | 稳定的性格特征（**需满足"非单次行为"约束**） |
| 习惯 | 行为模式、日常偏好、固定做法 |
| 对话风格 | 用词、句式、口头禅、语气、长度、是否爱用比喻等 |
| 经历 | 时间线化的关键事件 |
| 关系 | 与已知其他人物的关联（指向关系档案） |

### 4.2 关系档案（Relationship）必须覆盖

| 维度 | 说明 |
| --- | --- |
| 共同经历 | 双方/多方共同出现的事件与时间线 |
| 互动模式 | 谁先开口、谁回应、是否互相打断、强弱关系等 |
| 情绪与表达习惯 | 对彼此时的情绪倾向、称呼方式、语气变化 |
| 双方不同视角 | **同一件事分别记录每个人的视角**，不合并成"唯一真相" |
| 时间变化 | 关系随时间演变（如早期/后期不同） |
| 群体互动 | **3 人及以上时额外考虑**：联盟、站队、被冷落、传话等 |

### 4.3 系统能力要求（非功能性但必须设计）

- 长期记忆：跨会话保存、检索、更新、删除
- 多人多轮对话
- **动态发言者选择**：每轮由系统决定谁说话，并**记录选择理由**
- 预算限制：可设定上限，接近上限时告警，超出时暂停
- 任务恢复：断点续跑
- 自动化测试：有固定的测试素材与可重复运行的评测

## 5. 明确不做的事情（Out of Scope）

| 编号 | 不做的事 | 原因 |
| --- | --- | --- |
| N-1 | 网页 / 图形界面 | 初期采用本地 CLI，降低复杂度 |
| N-2 | 训练或微调自己的基础模型 | 成本与复杂度远超当前目标 |
| N-3 | P0–P5 阶段接入真实搜索 / 模型 API | 先做离线可验证的管线；Provider 只做接口与假实现 |
| N-4 | 让用户逐条审核证据 | 违反「普通用户零负担」目标 |
| N-5 | 生成面向用户的长篇研究报告 | 内部产物保留，但不作为交付物 |
| N-6 | 硬编码任何特定人物的设定/事实/关系/标准答案 | 项目必须通用化 |
| N-7 | 让 AI 模拟的对话反向改写真实人物档案 | 硬性红线，见 §6 |
| N-8 | 对冲突做出"谁对谁错"的裁决 | 只允许保留与标注 |
| N-9 | 多租户、登录鉴权、云端同步 | 本地单人工具 |
| N-10 | 实时语音、流式多人合成 | 与文本对话无关 |
| N-11 | 引入不必要的第三方复杂依赖 | 保持依赖最小化 |
| N-12 | 自动发布到任何外部平台 | 涉及对外发声，风险高 |

## 6. 内容与真实性的边界（硬性规则）

### 6.1 四类内容必须严格区分

> 字段名统一为 **`namespace`**（P1.2-A 更名，原记为 `origin`）。

| 类别 | `namespace` | 说明 | 能写到哪 |
| --- | --- | --- | --- |
| 公开来源原始资料 | `PUBLIC_SOURCE` | 来自公开资料的证据（含虚构作品的正式剧情与官方设定） | `Source` / `SourceEvent` / `EvidenceItem` |
| 系统推断 | `SYSTEM_DERIVED` | 档案与推断，推断必须记录 `derived_from` | `PersonaProfile` / `RelationshipProfile` / `EvidenceItem`（tier = INFERENCE） |
| 用户输入 | `USER_PROVIDED` | 用户在命令里补充的内容 | 单独登记为 `UserInputRecord`，**不混入公开资料证据** |
| AI 模拟事件 | `SIMULATED` | 对话中发生的任何事 | **只能写 `MemoryItem`，永远不能写 `EvidenceItem` / `PersonaProfile` / `RelationshipProfile` / `SourceEvent`** |

**补充红线**：虚构作品中的正式剧情资料（来自 `PUBLIC_SOURCE`，带 `canon_level`）**不得与 AI 自行生成的剧情混为一谈**。AI 无创建 `SourceEvent` 的路径，也无权把任何内容标记为 `CANON`。

### 6.2 不可违反的四条硬约束（Invariants）

| 编号 | 约束 |
| --- | --- |
| INV-1 | `Dialogue` 模块对 `EvidenceItem` / `SourceEvent` / `PersonaProfile` / `RelationshipProfile` **只可读，不可写** |
| INV-2 | 任何 `namespace = SIMULATED` 的数据，禁止出现在 `EvidenceItem` 表中 |
| INV-3 | `MemoryItem` 中来源于模拟的条目，禁止被提升或复制为其它命名空间 |
| INV-4 | 冲突记录只能新增与标注，**不得删除或合并**任何一方的说法 |

这四条必须有**自动化断言测试**（`INTERFACES.md` §10.3、`ROADMAP.md` P1.2-B 与 P5）。

## 7. 验收标准（Acceptance Criteria）

以下为**整个项目**的验收标准；各阶段的分段验收见 `ROADMAP.md`。

### A. 功能验收

| 编号 | 标准 |
| --- | --- |
| AC-1 | 输入 2 个人名，一条命令可跑完「研究 → 证据 → 人物档案 → 关系档案 → 对话」全流程 |
| AC-2 | 输入 3 个人名时，关系档案中包含群体互动维度 |
| AC-3 | 任意一条人物档案条目，可通过 ID 反查到至少 1 条证据；任意一条证据可反查到来源 |
| AC-4 | 同一来源被多次检索到时，只登记 1 条来源记录（去重生效） |
| AC-5 | 存在冲突时，冲突记录中包含**至少 2 种说法**及其来源，且任务未中断 |
| AC-6 | 全部证据都带有 `tier` 标记，`INFERENCE` 不与前三者混排 |
| AC-7 | 单人单次行为的描述，不会出现在"稳定性格特征"字段中 |
| AC-8 | 对话中每轮输出都记录了「发言人 + 选择理由」 |
| AC-9 | 关闭程序后重新打开，之前对话中发生的事仍能被检索到（记忆持久化生效） |
| AC-10 | 删除某条记忆后，后续对话不再引用它 |
| AC-11 | 任务中断后 `resume` 可从上次检查点继续，不重复已完成阶段 |
| AC-12 | 达到预算上限时任务暂停并提示，不会静默继续消耗 |

### B. 安全与真实性验收

| 编号 | 标准 |
| --- | --- |
| AC-13 | 自动化测试断言：`Dialogue` 运行后，`Evidence` 表数据**零变化** |
| AC-14 | 自动化测试断言：模拟对话中生成的语句，不会被任何后续检索当作"该人物的原话"返回 |
| AC-15 | 冲突记录不会被自动清理或合并 |

### C. 通用化验收

| 编号 | 标准 |
| --- | --- |
| AC-16 | 全仓库检索（代码 + 配置 + 测试素材）不含任何真实特定人物的姓名、专属设定或"标准答案" |
| AC-17 | 测试素材全部为**合成的虚构人物**，可脱离网络运行 |
| AC-18 | 替换一组不同的人名与素材，系统无需改代码即可跑通 |

### D. 工程验收

| 编号 | 标准 |
| --- | --- |
| AC-19 | 所有 Provider 调用可被替换为本地假实现，测试全程不联网 |
| AC-20 | 模块依赖方向符合 `ARCHITECTURE.md` 的分层规则，无循环依赖（有自动检查） |
| AC-21 | 所有文档与代码中的术语一致（术语表见 `ARCHITECTURE.md` §2） |

## 8. 术语约定（快速对齐）

| 术语 | 含义 |
| --- | --- |
| Project（项目） | 一次完整的「输入对象 → 产出对话」容器（原 `Run`） |
| PersonEntity（模拟对象） | 被模拟的对象，可为真人也可为虚构角色 |
| Source（来源） | 一份公开资料（网页、报道、访谈视频等） |
| SourceEvent（来源事件） | 来源内可定位的原始事件（一次采访、一集剧情、一次官方发布） |
| EvidenceItem（证据） | 从来源中提取出的一条**原子化**说法 |
| Claim（断言） | 证据或档案中的一条具体陈述 |
| Tier（证据级别） | `VERBATIM` / `PROFILE_BACKGROUND` / `THIRD_PARTY` / `INFERENCE` |
| namespace（来源世界） | `PUBLIC_SOURCE` / `SYSTEM_DERIVED` / `USER_PROVIDED` / `SIMULATED` |
| EntityType（对象类型） | `REAL_PERSON` / `FICTIONAL_CHARACTER` |
| PersonaProfile（人物档案） | 一个对象的结构化档案 |
| RelationshipProfile（关系档案） | 两个或多个对象之间的关系档案 |
| MemoryItem（记忆） | 对话过程中产生的、需要跨轮次保留的信息 |
| DerivedArtifact（派生产物） | 记忆的摘要 / 索引 / 缓存 |
| Checkpoint（检查点） | 任务续跑所需的阶段性落盘状态 |

> ⚠️ **Tier 与 namespace 是两个不同的维度**，不要混淆。Tier 表示「这是哪一类说法」，namespace 表示「这个说法来自哪个世界」。详见 `DATA_MODEL.md` §1。
> 术语全集以 `ARCHITECTURE.md` §2 为准；接口细节以 `INTERFACES.md` 为准。

## 9. 本规格的开放问题

以下问题**尚未决定**，需要在进入 P1 前讨论。详见 `DECISIONS.md` §3。

- 人物重名时是否中断询问用户
- 公开资料的获取渠道与合规边界
- 存储选型（SQLite / JSON 文件 / 其他）
- 预算的计量单位与超预算行为

- 模拟记忆的留存策略
- 无标准答案时如何评测质量
