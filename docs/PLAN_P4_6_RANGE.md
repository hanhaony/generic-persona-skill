## 2. 四项候选逐项说明

### P0-1（新增建议）：业务链装配层 / composition root

> 这一项不在你给的四条里，但它是 P0/P1/P2/P3 里**三项的共同阻塞项**，单独做掉最省事。

**现状**

- `BusinessOrchestrator` 只被 `scripts/e2e_p4_5a.py` 与 `tests/` 装配；
- `persona/cli/main.py` 里只有一句说明文字提到它，**没有任何构造 `BusinessDeps` 的代码**；
- 结果：所有能力（含 G6/G7/G9 的修复）的"产品路径"目前是**测试脚本**，不是 CLI。

**为什么不行**

- 任何"装配进产品代码"的需求（分析器、真实检索、账本落库）都会各自在脚本里再写一遍装配，
  于是出现第二个、第三个 composition root——这正是 G4 当初"脚本代劳掩盖缺陷"的同型风险。

**做完能解决什么**

- 一个 `build_business_stack(settings, *, analyzer=None, source_provider=None, ...)` 工厂，
  CLI 与脚本共用；后续 P0/P1/P2/P3 只改工厂，不改调用方。

**依赖**：无（纯重构 + 一个薄 CLI 入口）。**验收**：CLI 能跑一次五阶段业务链（离线 Mock）；
脚本改为调用工厂，行为逐字不变（`test_p4_5a_e2e` 82 项仍全绿）。**真实调用**：否。

**优先级：P0**（先做，否则后面三项各写一遍装配）

### P0-2：G11 系统级累计闸门（账本落库）

**现状（几条关键事实，比"纯内存"更具体）**

1. `ExternalUsageLedger.__init__` 只接 `max_unknown_requests` / `unknown_hold_credits`，
   **没有任何 hydrate 入口**，`_records` 每次从空开始；
2. **落库表已经存在**：`external_usage_records`（`storage/schema.py:85`），
   主键 `idempotency_key`，含 `cost_estimate/cost_confirmed/cost_status/task_id/run_id`；
3. **写库端口已经存在**：`SqliteStorage.record_external_usage()`（幂等，主键冲突即忽略）、
   `has_external_usage()`（跨轮幂等只读查询）、`external_usage_report()`；
4. 消费侧端口也已存在：`ProviderClaimExtractor(usage_sink=...)`、`ResearchDeps.usage_sink`；
5. **但装配层没接**：e2e 脚本构造抽取器与 `ResearchDeps` 时都没传 `usage_sink`，
   ⇒ C 轮真实运行的花费**没有落进任何库**（只活在进程内存里）；
6. `effective_max_cost()` 的 docstring 明确写着：总上限与单任务上限**暂取更严的那个**，
   "$1.00 项目级封顶"是遗留项——两层计数从未实现。

**为什么不行**

- 0.25 USD 是**每次进程**的上限。跑 100 次就是 25 USD，系统一声不响；
- 跨轮幂等也不完整：`has_external_usage()` 已能查，但没接线 ⇒ 换个进程重跑会重新花钱；
- 人工记账（`RUNNING.md` §5.15）能兜住"账"兜不住"闸门"。

**做完能解决什么**

- 新进程启动时从库 hydrate 累计花费 ⇒ 全局上限真正生效；
- 跨进程重复请求被 `has_external_usage()` 拦下（与内存账本形成双保险）；
- 人工累计账可自动生成，不必再手算。

**依赖**：P0-1（装配层没做的话，落库又要写在脚本里）；`STORAGE_*` 错误码语义（已有）。

**验收标准（离线可验）**

1. 同一 SQLite 文件，进程 A 花 0.10 → 进程 B 启动后 `occupied_cost()` ≥ 0.10；
2. 全局上限设为 0.15 时，进程 B 在发请求**之前**返回 `BUDGET_EXCEEDED`（0 次调用）；
3. `cost_status=UNKNOWN` 的历史笔数按保守值计入（不得当 0）；
4. 同一 `idempotency_key` 跨进程重放 → 被拦，`requests` 不增；
5. 迁移：**不需要**（表已存在，`CREATE TABLE IF NOT EXISTS` 对旧库平滑）；
6. 全量回归全绿 + 新增 ≥10 项测试。

**真实调用**：否。**成本**：0。

**优先级：P0**（费用安全，且工作量比预想小）

### P1：traits 非空路径

**现状**

- `judge_stability`（`evidence.py:1052`）规则：`occurrences≤1 → SINGLE`、
  `distinct_sources≥3 → PATTERN`、否则 `REPEATED`；
- `_assess_stabilities` 组内**按 `source_id` 去重**（G6-D2）⇒ 有来源证据的
  `occurrences` 恒等于来源数；
- 分组键 = (归一化 claim, 主体集合)，归一化**只折空白**，不做语义聚类；
- C 轮实测：16 条证据全 `SINGLE`，`traits=0`。

**为什么不行**

- 现在能进 `traits` 的唯一路径是"同一句话、同一主体、来自 ≥2 个不同来源"；
  而三份材料措辞互不相同 ⇒ 结构性为空；
- 换个说法描述同一个性格（"沉默寡言" vs "很少与人交谈"）永远进不了 `traits`。

**关键判断（会改变工作量）**

> **"同句多源"很可能不需要改产品代码。** 规则已经支持，缺的是**材料与断言**：
> 两份独立来源含**逐字相同**的句子 + 模型输出**相同措辞**的 claim。
> 但"模型输出相同措辞"不可控 ⇒ 这条路径应该用**受控输入**验（种子证据或固定载荷），
> 而**不是**拿真实模型赌它两次措辞一致。

**做完能解决什么**

- P1a（同句多源）：证明"稳定特征确实能进 traits"，把 AC-7 的正向路径补齐
  （现在只验证了负向：单次不进 traits）；
- P1b（语义聚类）：让"换说法但同义"也能累计，这是**新能力**，需要模型参与。

**依赖**：P1a 无依赖；P1b 依赖一个"claim 归一"决策（见 §5）。

**验收标准**

- P1a：同一 claim（归一化后完全相同）来自 2 个不同 `source_id` ⇒
  `stability_verdict.stability=REPEATED`、`occurrences=2`、`distinct_sources=2`，
  且该条目**出现在** `traits`；同时 `stability` 列仍为 `UNKNOWN`；
- P1a 反向：同一来源内两次出现 ⇒ 仍 `SINGLE`、不进 `traits`（G6-D2 不能被绕过）；
- P1b：只有**人工标注的同义组**被判为同组，且误合并率可量化（需要标注集）；
- 红线：任何情况下 `SINGLE/UNKNOWN` 不得进 `traits`（AC-7 不放宽）。

**真实调用**：P1a 否（零成本）；P1b 是（需模型做归一）。

**成本估算**

| 子项 | 估算 |
| --- | --- |
| P1a | 0（离线，种子/固定载荷） |
| P1b 单次运行 | 约 **0.004~0.006 USD**（按 C 轮实测单价：聚类输入 ≈ 6.5K in / 2K out） |
| P1b 调参轮次 | 建议上限 **≤0.05 USD**（约 8~10 次），另需单独授权 |

**优先级：P1**（P1a 便宜且能补上 AC-7 的正向证据；P1b 先出方案再谈）

2. A→B 与 B→A 的内容**分别存储**，无"综合定论"字段被写入；
3. 每条 `view_of_targets` 条目带 `evidence_refs` 且全部命中已登记证据；
4. 分析器返回 `Err` 时：**降级到兜底**并留告警，不得静默吞掉（同 G5/G9 口径）；

**真实调用**：规则分析器 **否**（零成本、离线可验）；模型分析器需单独授权。

**成本估算**：规则路径 0；模型分析器单次约 **0.002~0.004 USD**（输入为本次证据集，约 1~2K tokens）。

**优先级：P2**（规则路径就能让字段从"永远空"变成"有内容且可追溯"，性价比最高）

### P3：H-17 真实检索

**现状（比"没实现"更准确）**

- `TavilyProvider` 的 `search()` **与** `extract()` **都已实现真实 HTTP**
  （`/search`、`/extract`，含 `include_usage`、幂等键、按官方 credits 结算）；
- `ResearchService._maybe_extract` 已实现"提取前合规检查 → 预留 → 抓取 → 结算"；
  但 `extraction_strategy=None` 时**不抓正文**，且抓到的全文**只留内存**（默认不落库）；
- `ResearchDeps.compliance` 是可选 `ComplianceHook`，`None` = 不查；
- 合规/隐私两条决策 **仍未拍板**：`DECISIONS.md` Q-02（资料获取渠道 + robots/ToS + 是否存快照）、
  Q-03（是否支持在世人物、隐私边界）——两条都标着"P2 前"，至今空白；
- 数据源选择：`providers/registry.py` 能造 `TavilyProvider`，但业务链没配过它。

**为什么不行**

- 现在整条链的"研究"是桩：合成人物在公网不存在，所以桩是**必要**的；
  但这也意味着"真实人名的完整链路"**一次都没跑过**；
- 合规钩子为 `None` ⇒ 抓取没有任何域名/robots/ToS 约束；
- 质量波动：真实网页有导航栏、广告、PDF、反爬页面，`assess_content_quality` 会把它们判
  `LOW_QUALITY`，但不保证有足够材料进抽取器。

**做完能解决什么**

- 用户输入真实人名 → Tavily 检索 → 正文抓取 → 门禁 → 模型抽取 → 档案，全链真实；
- 但**必须先有 Q-02/Q-03 的规则**，否则抓取行为没有依据。

**依赖（硬阻塞）**

1. Q-02 合规规则（robots/ToS、是否存页面快照、域名策略）；
2. Q-03 隐私边界（是否只限公众人物/已故人物、在世人物的处理）；
3. Tavily API Key（`PERSONA_SEARCH_API_KEY`，目前未配置）；
4. P0-2（真实检索会**花 credits**，没有跨进程累计闸门就等于没有总控）；
5. 质量波动预案（多来源冗余、重试上限、失败降级）。

**验收标准**

1. 真实人名链路跑通：来源 ≥2、正文门禁 `VALID` ≥1、证据 ≥1、档案 1 份；
2. 每个来源可追溯（`source_id` ↔ URL），原始响应落盘；
3. 费用可见：search credits + extract credits 均 `CONFIRMED`，且落库；
4. 合规钩子有**可测的**拒绝用例（被 DENY 的 URL 不发请求、留告警）；
5. 质量波动控制：单次运行设"最少有效材料数"，不足则报告"证据不足"而不是硬凑。

**真实调用**：**是**（Tavily + 模型，各需单独授权）。

**成本估算**

- Tavily：`basic` search = 1 credit、`extract` 按每 5 次成功提取 1 credit 折算；
  一次 3 查询 + 3 抓取 ≈ **4 credits**。免费额度 1000 credits/月 ⇒ 单次可忽略，但**仍需 Key**；
- 模型：按 C 轮实测单价，材料变多/正文变长会把输入推高，单次估 **0.005~0.012 USD**；
- 建议设单次硬上限 0.05 USD，并**先做 1 次 3 查询的最小冒烟**。

**优先级：P3**（依赖最多、风险最高、且需要两条合规决策先落地）

## 3. 推荐执行顺序及理由

```
P0-1 装配层  →  P0-2 G11 落库  →  P2 规则分析器  →  P1a 同句多源  →  P1b 语义聚类  →  P3 真实检索
   (0 成本)      (0 成本)          (0 成本)          (0 成本)        (需授权)        (需授权+Key+合规)
```

1. **先装配层**：后面三项都要"装进产品路径"，不先做就会各写一遍 composition root，
   重复 G4 的老毛病。
2. **再 G11**：它是**费用安全**，且 P3 一旦开跑就必须先有它；同时它工作量被高估了——
   表和端口都在，缺的是 hydrate + 累计口径 + 接线。
3. **再 P2**：规则分析器已实现且已产出双向视角，这一项能把"永远空的三组字段"变成
   "有内容且可追溯"，是**投入产出比最高**的一项，且零成本。
4. **再 P1a**：同句多源大概率不用改产品代码，只需受控材料 + 断言，用来补 AC-7 的**正向**证据。
5. **P1b 语义聚类**放到 P1a 之后、P3 之前：它需要一个新的"claim 归一"决策与模型授权，
   但对 P3 有价值（真实网页措辞更杂）。
6. **最后 P3**：两条合规决策没拍板之前不应动手；且它需要 Key、需要累计闸门（P0-2）、
   需要质量波动预案。先做小的，会留下"跑通了但没约束"的技术债。
